# ロスレスカットの実装知識

→ 入口: [overview.md](overview.md)

カット処理を実装する / 直すときはこの文書を読む。**すべて実測に基づく。**

## 基本方針

再エンコードしない。よって切れる位置は**キーフレーム（同期サンプル）境界に限られる**。

保持区間 `[S, E)` に対し、**外側にスナップする**（本編を削らず CM を残す）:

- 開始 `S` → **手前**の同期サンプルへ戻す
- 終了 `E` → **次**の同期サンプルへ伸ばす

対象ファイルの GOP は 4.004 秒固定でシーンチェンジ IDR がないため、境界あたり平均 2.1〜2.5 秒の CM が残る（[measurements.md](measurements.md)）。これは許容する方針で決定済み。

## 【最重要】切り出しはパケット数で行う

### 正しい規則

> **S の同期サンプルから、デコード順にちょうど `E - S` パケット取る**

閉じた GOP なら常に成立する（2 つの IDR の間にあるデコード順パケットの集合 == その間に表示されるフレームの集合）。並べ替え深度を知る必要がない。

### 時間指定は使ってはいけない

`ffmpeg -t <(E-S)フレーム分>` は **B フレームの並べ替え深度ぶん余分にパケットを取り込む**。実測（対象素材では深度 2）:

| 指定 | 得られるパケット数 | 表示順 |
|---|---|---|
| `-t (N フレーム分)` | **N + 2** | **穴が空く** |
| `-t (N-2 フレーム分)` | N | 正常 |

穴の実例（セグメント末尾の pts を昇順に並べたもの）:

```
2515 2516 2517 2518 2519 2522     ← 2520, 2521 が欠落
```

**この破綻はエラーを出さない。** フレーム数も一見合ってしまう。表示順の連続性を検査しない限り気付けない。

補正値 `2` は素材の並べ替え深度であり、エンコーダ設定（`--bframes` / b-pyramid）で変わる。索引から dts を引いて切断時刻を計算する方法も試したが、ffmpeg 側の判定基準と一致せず**一貫して +1 パケット**になった（5 区間すべてで再現）。**時間ベースの切断はどう計算しても補正値が必要になるため、根本的に不適切**という結論。

### 前提条件と検査

- **閉じた GOP が前提。** dtvindex の `leading_frame_count` が 0 であることを確認する（対象 3 ファイルはすべて 0）。オープン GOP（x265 の既定など）では CRA に先行ピクチャがあり、この規則が成立しない
- 区間ごとに以下を assert する:
  1. パケット数 == `E - S`
  2. 表示順（pts 昇順）に欠落がない
  3. 先頭パケットが同期サンプル

## 【最重要】無劣化の検証に md5 を使ってはいけない

### 誤った方法

Annex B 変換した映像 ES の md5 比較。`h264_mp4toannexb` が **IDR ごとに SPS/PPS を再挿入する**ため、セグメントの切り方が違うだけでハッシュが変わる。

実際に起きたこと: バイト数は完全に一致（701,491,266 bytes）するのに md5 が異なり、最初の相違はセグメント境界付近だった。**3 ファイル中 2 本で md5 が一致したのは偶然**。

### 正しい方法

ffprobe のパケット単位ハッシュ:

```console
$ ffprobe -v error -select_streams v:0 \
    -show_entries packet=data_hash -show_data_hash CRC32 \
    -of csv=p=0 FILE.mp4
CRC32:89a79bab
CRC32:6446a928
```

参照側は `-ss <t> -frames:v N` で取り出す（`-frames:v` は厳密にパケット数を数えるので決定的）。

音声については「出力の全パケットが元ファイルに存在するか」を集合比較すると、境界パケットの選択差に影響されず確認できる:

```console
$ ffprobe ... IN.mp4  | sort -u > src.txt
$ ffprobe ... OUT.mp4 | sort -u > out.txt
$ comm -23 out.txt src.txt | wc -l      # 0 なら全パケットがビットコピー
```

**`src.txt` / `out.txt` が空でないことを先に確かめること。** 両方が空でも `comm` は 0 を返すため、ffprobe がパケットを1つも返していない（引数を間違えた等）ときに「全パケットがビットコピー」と区別がつかない。`src/verify.rs::verify_audio_packets_with_ffprobe` は同じ理由で0件を明示エラーにしている。

## 音声の扱い

### 連結自体は可能（再エンコード不要）

Opus / AAC をはじめ mp4-atom が認識する音声 Codec はパケット単位で独立しており、パケット列を連結すれば有効なストリームになる。カット処理はパケットをビットコピーするだけでコーデックに依存しない（判定は `src/mp4io/read.rs::is_audio_codec`、対応一覧は [mp4-atom.md](mp4-atom.md)）。Opus / AAC は実測で全パケットがビットコピーであることを確認済み。

### 継ぎ目に MDCT の過渡が出る

MDCT の窓が重なるため、**継ぎ目の最初の 1 パケット（Opus で 20 ms）は前フレームの窓がないので正しく復号されない**。クリックノイズが出うる。

**許容する。** カット点は chapter_exe が無音として検出した位置であり、かつ外側スナップにより継ぎ目は**残存 CM マージンの内側**に来る。つまり違和感が出る箇所は CM の範囲内。ユーザー確認済みの判断。

厳密な対処（preroll を含めて edit list / `skip_samples` で捨てる）は mp4 の途中に複数の edit list エントリを置くことになり、プレイヤ互換が悪いので採らない。

### 【最重要】音声パケットはソース上の位置から選ぶ

**音声パケットのグリッド（例: Opus 20 ms、AAC 1024 サンプル ≒ 21.3 ms @48kHz）と映像 33.37 ms グリッドは一致しない**ため、区間ごとに端数が出る。放置すると継ぎ目ごとにずれが蓄積しうる。以下の規則はグリッド長を仮定せず各サンプルの実 duration を累積するのでコーデックに依存しない。

正しい規則:

> 区間 `k` に割り当てる音声パケットは、**その区間の先頭サンプルのソース上の DTS** `dts_src(S_k)` に最も近いパケットから始め、その区間の映像長ぶん取る。
>
> 目標時刻は毎回**ソースの絶対時刻**から引き直す。出力側の累積時間を起点にしてはいけない。

`dts_src(S_k)` は「保持する / しない」に関係なくソース先頭からの絶対時刻なので、区間を跨いで誤差が積み上がらない。丸め誤差は区間ごとに独立して ±半パケット（Opus なら約 10 ms）以内に収まる。

**合成時刻（pts = dts + cts_offset）ではなく DTS を使う。** 書き出しは `ctts` を引き継ぐので、出力の pts は次の関係になる:

```
output_pts(i) = T_{k-1} + source_pts(i) - dts_src(S_k)
                （T_{k-1} = それ以前の区間の映像長の累積 = 出力タイムライン上の区間開始）
```

つまり**出力タイムラインへのシフト量は `dts_src(S_k)`**。ここに pts を使うと、区間先頭サンプルの `cts_offset`（= 並べ替え深度、実測 2 フレーム = 66.7 ms）ぶん音声が映像より先行する。→ 下記「実際に起きた誤り 2」

音声サンプルの `duration` は一定と仮定してはいけない。実データでは**先頭パケットがエンコーダのプライミング分だけ大幅に長い**（実測: 20 ms が並ぶ中で先頭だけ 80 ms 相当）。`audio_samples[0].duration` を frame_size とみなして除算すると、この 1 個の外れ値で全境界がずれる。各サンプルの実際の `duration` を累積した表に対して最近傍を探す。

Amatsukaze の `fillAudioFrames`（`StreamReform.hpp:1287-1420`）が同じことをしている（「映像の時刻まで音声を進める、足りなければ水増し、行き過ぎればスキップ」＋ `AudioDiffInfo` で統計出力）。TS の PTS が乱れる前提の複雑な実装だが、mp4 では PTS が連続なのでソース時刻からの直接引き当てに簡略化できる。

**実測**: 5 区間の出力で映像 2754.690 秒 / 音声 2754.659 秒（差 **-31 ms**）。ただし**これは合計の長さしか見ていない測定であり、下記の位置ずれを検出できなかった**。

### 実際に起きた誤り 1: 出力の累積時間で音声を詰めた（修正済み）

`select_audio_segments` が区間のソース位置を見ず、直前の区間の終端パケットを起点に「**出力**の累積映像時間」で終端だけを決めていた。結果、**出力の音声は常にソースの先頭から詰められ**、2 区間目以降がそれまでに除去した合計時間ぶん先行した。

再現（音声を周波数スイープにしたフィクスチャで確認。定常サイン波だと全パケットが同一バイト列になり、この誤りは検出できない）:

```
保持区間 = frames [360,480) → ソース時刻 12.012s〜16.016s
出力の音声先頭 3 パケット: 097d0092, e652967a, 7cd61a94
元ファイルの  0.000s〜:    097d0092, e652967a, 7cd61a94   ← 一致（誤り）
元ファイルの 12.000s〜:    e9a0cc5d, 5620c06d, afed7d67   ← 本来こちら
```

**自己検証を素通りした理由が重要で、音声側の既存の検査はどちらも位置を見ていない**:

- 集合比較（上記「無劣化の検証」）は「出力の全パケットが元ファイルに存在するか」しか見ない
- 区間ごとの A/V 長さ比較は、長さが合っていれば通る

よって音声には「**ソース上の正しい位置から取れているか**」を直接見る検査が必要。区間ごとに、出力側のその区間の先頭音声パケットの CRC32 が、元ファイルの `dts_src(S_k)` 近傍のパケットの CRC32 と一致することを確認する。フィクスチャの音声は時間変化するもの（周波数スイープ等）にしておくこと。

### 実際に起きた誤り 2: 目標時刻に pts を使った（修正済み）

誤り 1 を直したときに、目標時刻を区間先頭サンプルの**合成時刻**（pts）にしてしまった。ソース位置から引き当てる形にはなったが、**音声が映像より約 67 ms（区間先頭サンプルの `cts_offset` = 並べ替え深度 2 フレーム）先行する**状態だった。

実測（`Trim(360,479)` を保持）:

```
元ファイル: 映像 frame 360 の pts = 12.079s / 選ばれた音声先頭 = 12.080s  ← 元では同時刻
出力:       同じフレームの pts = 0.0667s    / その音声が出力 0.000s に置かれる
            → 出力 0.0667s の時点で鳴っている音声はソース 12.147s 相当（67 ms 先行）
```

**この誤りも既存の検査を素通りした**:

- 区間ごとの A/V 長さ比較は、長さが合っていれば通る（定数のオフセットは見えない）
- 誤り 1 用に足した「先頭パケットの位置」検査も、期待位置を同じ pts 基準で計算していたため一致してしまう

検出するには、**元ファイルと出力で「映像 pts − 音声 pts」の関係が保たれているか**を見る必要がある（区間先頭について 1 音声パケット長以内で一致すること）。期待値を実装と同じ式で計算する検査は、式そのものが間違っているときに無力である、という教訓。

## キーフレーム境界スナップの計算

**`stss` から得た実際の同期サンプル列に対して最近傍を二分探索する**（`src/plan.rs::snap` の `floor_or_equal` / `ceil_or_equal`）。

```
S_snapped = S 以下で最大の同期サンプル   ← 手前の同期サンプル
E_snapped = E 以上で最小の同期サンプル   ← 次の同期サンプル
```

**等間隔を仮定したコードを書かないこと。** `floor(S / KFI) * KFI` のような式は対象ファイル（GOP 120 フレーム固定）では偶然一致するが、シーンチェンジ由来の IDR が 1 つ入るだけで壊れる。実装には等間隔前提の分岐を置いていない。

該当する同期サンプルが無い場合は端で止める（開始はファイル先頭 0、終了は総フレーム数）。

スナップ後に区間が重なる可能性を検査する（今回の実データでは発生しなかったが、保持区間が近接している場合に起こりうる）。

## CM 側（除去した区間）を別ファイルに出す

検出が当たっているかを目視確認するために、**捨てた側**も同じ品質で出力する。「CM として切った中に本編が入っていないか」を見れば、切りすぎ（本編の欠落）をそのまま検出できる。

### 補集合は追加のスナップを必要としない

保持区間の集合 `{[S_i, E_i)}` の**補集合をそのまま区間リストとして使える**。外側スナップ後の `S_i` は手前の同期サンプル、`E_i` は次の同期サンプルなので、補集合 `[E_i, S_{i+1})` の両端も必ず同期サンプル上にある。したがって上記「S の同期サンプルから `E - S` パケット取る」規則が補集合にもそのまま成立し、**スナップ処理・音声選択・書き出し・自己検証をもう一度呼ぶだけ**で済む。

境界ケース（いずれも空区間になるので捨てる）:

- 先頭の保持区間が 0 から始まる → 先頭の補集合は空
- 最後の保持区間の終端がファイル末尾 → 末尾の補集合は空
- 終端が「同期サンプルが無く `total_frames` にフォールバック」した → 続く補集合は空

`--snap inward` では保持区間が退化（`end < start`）しうるため、補集合の順序も壊れる。inward と CM 出力の併用は拒否する。

### 両方出すこと自体が強い検査になる

保持側と CM 側の**フレーム数の合計が元ファイルの総フレーム数と一致し、かつ `DecodeIdx` の集合が互いに素**であることを assert する。境界が 1 フレームでもずれれば必ず落ちる。

**実測**（20 秒 599 フレームの合成ファイル、`Trim(360,479)` を保持）: 保持側 120 パケット / CM 側 479 パケット、合計 599。自己検証 4 項目とも通過。

### 意味の非対称性

外側スナップでは残存 CM は**本編側**に出る（境界あたり 2.1〜2.5 秒）。よって:

- CM ファイルに本編が映っていた → 検出が切りすぎた。**この機能で見つかる**
- 本編ファイルに CM が残っている → 仕様どおり。CM ファイルからは判断できない

## 参考: 検証で通した手順

実際に 3 ファイルで通した手順。`-t` の補正値に依存しているため**本実装ではパケット単位選択に置き換えるが**、比較対象の生成には使える。

```bash
# 区間ごとに切り出し（N は区間のフレーム数、depth は並べ替え深度）
ffmpeg -ss <t(S)+0.005> -i IN.mp4 -t <(N-depth)/fps> \
       -c copy -map 0:v:0 -map 0:a:0 seg$i.mp4

# 連結
ffmpeg -f concat -safe 0 -i list.txt -c copy -movflags +faststart OUT.mp4
```

`-ss` に +0.005 秒足しているのは、浮動小数点でキーフレームの手前に落ちるのを避けるため（1 フレーム = 33.4 ms に対して十分小さい）。
