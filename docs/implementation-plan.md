# 実装計画

→ 入口: [overview.md](overview.md)

## コマンド構成

**解析とカットを分ける。** 検出の見逃しが実際に起きており（[jls-settings.md](jls-settings.md)）、目視確認と手動修正を挟む必要があるため。

```
tachikaze analyze IN.mp4 -o trim.avs [--report]
    1. dtvindex build              （外部プロセス）
    2. chapter_exe                 （外部プロセス）
    3. join_logo_scp               （外部プロセス）
                                   -set autocm_sub 11 -set param_cuttr 1 を既定付与
    4. --report で以下を出力
       ・各カット境界とキーフレームの距離
       ・余分に残る合計秒数
       ・見逃し候補の警告（既知の CM ブロック長と一致する未カット区間）

（必要なら trim.avs を人手で編集）

tachikaze cut IN.mp4 --trim trim.avs -o OUT.mp4 [--snap outward|inward]
    5. mp4-atom でサンプル表を読み、表示順↔デコード順を導出
       → .dtvi と一致するか assert（不一致なら停止）
    6. Trim をキーフレーム境界へスナップ（既定 outward）
    7. 映像: デコード順に (E-S) サンプルを選択
    8. 音声: 区間ごとに開始パケットを選び、累積誤差を持ち越し
    9. mp4-atom で書き出し（stsd は clone、サンプル表のみ再構築）
   10. 自己検証
```

一括実行用の `tachikaze auto` は後から足せる。

## 型設計の要点

**表示順とデコード順を別の型にする。** この 2 つの混同が唯一の重大バグ源であり、混同するとエラーを出さずに間違った位置で切る。

```rust
struct DisplayIdx(u32);   // 表示順（Trim / .dtvi の frame_number）
struct DecodeIdx(u32);    // デコード順（mp4 のサンプル番号 / .dtvi の sample_number）
```

相互変換は明示的な関数だけを通す。

## 自己検証（手順 10）

区間ごとに以下を assert し、1 つでも失敗したら**出力を破棄して停止**する:

1. 映像パケット数 == `E - S`
2. 表示順（pts 昇順）に欠落がない
3. 先頭パケットが同期サンプル
4. `.dtvi` のフレーム番号と自前導出が一致

加えて全体で:

5. 音声の累積誤差の最大値をログ出力（`AudioDiffInfo` 相当）
6. `--verify` 指定時は ffprobe のパケット単位 CRC32 で元ファイルとの一致を確認（[lossless-cut.md](lossless-cut.md)）

## 実装順序

1. **`analyze` を先に作る。** 外部プロセスの起動と `--report` だけ。これだけで「どのファイルがどれだけ余分に残るか」を一括調査できる
2. **`cut` の映像パスのみ。** 音声を捨てて映像だけ出力し、パケット単位 CRC で無劣化を確認
3. **音声パスを足す。** ドリフト補正込み
4. **自己検証を組み込む**

手順 2 の骨格は検証コード 153 行として既に存在する（[mp4-atom.md](mp4-atom.md) に転記済み）。

## スコープ外（再掲）

| 項目 | 理由 |
|---|---|
| CM 検出アルゴリズム | 既存ツールが担当 |
| ロゴ検出 | delogo 済み mp4 では原理的に不可 |
| 映像の再エンコード | 数秒の CM 残りを許容する方針 |
| 音声の再エンコード | 継ぎ目のノイズは残存 CM の範囲内 |

**ただし「境界 GOP だけ再エンコードすればフレーム精度になる」ことは覚えておく。** 実測で境界あたり 4 秒（120 フレーム）分のエンコードで済む。30 分番組・8 境界なら 32 秒分。方針が変わったときの逃げ道として安い。

## 未解決事項

| 項目 | 状況 |
|---|---|
| `elst`（edit list）の扱い | **未検証。** 元ファイルに edit list があるとサンプルを削った後に整合しない可能性がある |
| `stsd` が複数エントリの場合 | **未検証。** `sample_description_index` を 1 固定にしている |
| 4 GB 超の出力（`co64`） | **未実装。** 現状 `stco` 固定 |
| `stts` / `ctts` のランレングス圧縮 | **未実装。** 1 サンプル 1 エントリだと 10 万サンプルで 800 KB になる |
| チャンクのインターリーブ | **未実装。** 現状トラックごとに 1 チャンク。プレイヤが大きくシークする |
| 継ぎ目ごとの A/V ずれ | 合計値は測ったが**個別は未検証** |
| オープン GOP のファイル | 対象 3 ファイルは閉じた GOP。**オープン GOP では「パケット数 == フレーム数」規則が成立しない** |
| 複数音声トラック / 字幕トラック | **未検証。** 対象ファイルは映像 1 + 音声 1 |
