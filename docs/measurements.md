# 実測データ

→ 入口: [overview.md](overview.md)

2026 年 7 月に実ファイル 3 本で測定した結果。**すべて実測値。**

## 対象ファイルの共通性質

| 項目 | 値 |
|---|---|
| 映像 | H.264 |
| 音声 | **Opus**（この 3 本が Opus だっただけで、ツールの対応範囲を表すものではない。対応する音声 Codec は [mp4-atom.md](mp4-atom.md)「音声トラックとして扱う Codec」を参照） |
| フレームレート | 30000/1001 (29.97) |
| **GOP** | **120 フレーム（4.004 秒）完全固定。ばらつきゼロ** |
| シーンチェンジ由来の IDR | **存在しない** |
| オープン GOP | なし（dtvindex の `leading_frame_count` = 0） |

Amatsukaze の出力ではない（Amatsukaze は AAC を出す）。Opus + 固定 4 秒 GOP は配信系トランスコードの典型的な設定。放送録画（H.264 + AAC）は字幕トラックや `elst` を持つことが多いが、これらは `tachikaze prepare`（字幕をサイドカーへ退避・`elst` を除去）が1回の ffmpeg 呼び出しで前処理する（[architecture.md](architecture.md)「未対応の入力」「コマンド構成」）。`auto` はこの `prepare` を先頭で自動的に呼ぶため、利用者が個別に前処理を意識する必要はない。

**この GOP 構造が本プロジェクトの設計を決めている。** シーンチェンジ検出が無効な設定でエンコードされているため、「CM 境界＝シーンチェンジ＝IDR」という期待が成立しない。

## ロゴの残存（E14-2）

2026 年 8 月、[E14](https://github.com/fetburner/Tachikaze/issues/89) の前提確認として追加実測。「delogo 済みの mp4 には局ロゴが残っていない」という記述（旧 overview.md / architecture.md）は実測に基づいていなかったため、解像度・放送局の異なる実録画で確認した。「ファイル別」表のファイル C を流用し、加えてファイル D〜F を新たに追加する（いずれも別番組・別局。番組名は書かない）。上の「ファイル別」表（2026年7月測定、3本）とは別に、この節だけで4本を追加測定した。

| | ファイル C（流用） | ファイル D | ファイル E | ファイル F |
|---|---|---|---|---|
| 局 / 種別 | MX2 / お笑い | BS11 / アニメ | TOKYO MX / アニメ（**ファイル A = MX1 と同局と思われる**。表記揺れのみで別局ではない） | BS 日テレ / アニメ |
| 解像度 | **720x480（SD、480p系。720p=1280x720 ではない）** | 1920x1080 | 1920x1080 | 1920x1080 |
| フレームレート | 30000/1001 | 30000/1001 | 30000/1001 | 30000/1001 |
| progressive / interlace | progressive | progressive | progressive | progressive |
| 局ロゴの有無（本編中、目視） | **残っているように見える**（非常に薄い透過。差分による裏付けは取れていない） | **残っている**（半透明で明瞭） | **残っている**（薄い透過。背景によっては判別しづらい） | **残っている**（半透明で明瞭） |
| 位置・大きさ（px、2 の倍数丸め、概算） | 右上。薄すぎて矩形を特定できず、`x≈600, y≈0` 付近の 120x40 の範囲内としか言えない | 右上。`x=1744, y=22, w=138, h=56` | 右上。`x=1670, y=70, w=180, h=20`（背景の柵模様と重なり誤差が大きい） | 右上。`x=1694, y=54, w=126, h=34` |
| CM 中の見え方 | スポンサー CM で消える（ただし上記のとおり本編側の「有」判定自体の確度が低い） | スポンサー CM で完全に消える。局の自主番宣（次回予告のバンパー）では**不透明な同じロゴに変わる**（透過度だけが変わり、消えはしない） | 実測した CM 区間（本編パートを模した映像コラージュの番宣）で消える | スポンサー CM で消える |

**追加で確認した1本（表には含めない）**: 同じく BS 日テレの別番組（ファイル F とは別ファイル。ユーザから提供された実録画）で `analyze` を通したところ、`chapter_exe` がほぼ全編を本編と判定し（`ffmpeg` が `missing picture in access unit` を警告するデコード異常のあるファイルだった）、CM区間との対比ができなかった。解像度は 1920x1080 でファイル D〜F と同じ（720p や別解像度の確認用ではない）。本編中のフレームにはファイル F と同じ位置・字体のロゴが確認できたため、「ロゴが残っている」こと自体は同じ局の別ファイルでも再現した。CM側との対比が取れていない一点だけを除いて記録する。

**測定方法**: `tachikaze analyze` で得た CM 境界（`--report` の出力）を使い、本編中・CM 中それぞれの位置を `ffmpeg -ss <秒> -frames:v 1` で 1 枚抜き出して目視比較した。矩形は、ロゴがある本編フレームを対象の角付近でクロップ・拡大（`ffmpeg crop` + `scale=...:flags=neighbor`）して目視で読み取った概算で、ファイル D は加えてロゴの無いスポンサー CM フレームとの差分（`blend=all_mode=difference`）でも位置を確認した。ファイル C はこの差分による局所化を試みたが、背景の絵柄との分離に失敗し断念した（表の「概算」止まりの理由）。

**見ていないこと**:
- 目視は各ファイル数点のみ。番組冒頭・終端でロゴの出方が変わるかは見ていない
- ロゴの不透明度は数値化していない（差分画像や拡大表示からの概算のみ）
- ファイル C・E の矩形はサブピクセル精度どころか有効数字も怪しい（薄すぎる、または背景の模様と重なり、差分ベースの局所化が背景との分離に失敗した）。特にファイル C は「残っている」判定自体も 1 点の目視のみで、差分による裏付けが取れていない
- 実際に確認したのは **720x480（SD）と 1920x1080（1080p）の 2 種類のみ**。1280x720（いわゆる 720p）は 1 本も確認していない。ロゴデータは対象と同じ解像度で作る必要があるため、720p 入力での挙動は未確認のまま残る
- 「ファイル別」表のファイル B（TBS）は今回の実測時点でキャッシュから消えており、再確認していない。この局でロゴが残っているかは未確認（ファイル A=MX1 相当はファイル E で確認できたため、未確認は TBS のみ）
- 4 局・5 ファイルとも「局ロゴが右上にある」という結果になったが、他の位置（左上等）にロゴを出す局があるかは未確認（サンプルの偏り）

**結論**: 確認した 4 局（MX2 / BS11 / TOKYO MX / BS日テレ）・5 ファイルすべてでロゴが残っていた（ファイル C は確度が低い目視のみ）。少なくとも一部の局では「delogo 済みなら不可」という前提は誤りだったと確定した。未確認の局・解像度（TBS、1280x720）にまで一般化できるかは分からない。この確認を根拠に [E14](https://github.com/fetburner/Tachikaze/issues/89) の自前ロゴ検出実装を進めた（実装は E14-1〜E14-8 で完了。実測は次節「ロゴあり/なしの比較（E14-9）」）。

## ロゴあり/なしの比較（E14-9）

[E14-9](https://github.com/fetburner/Tachikaze/issues/98) で、`analyze --logo` 実装（E14-8）を実際の録画ファイルに通した。**実ファイル 2 本**（上記「ロゴの残存」のファイル D = BS11 / アニメ、ファイル C = MX2 / お笑い）。`tachikaze make-logo` でロゴ矩形から `.lgd` を作り、`analyze --logo <path.lgd>` と `analyze`（`--logo` 省略）を同じ入力に対して実行し、`trim.avs`・`detail.jls`・`--report` の出力を比較した。

### make-logo の有効フレーム数

| ファイル | 矩形 | `--threshold` | 有効フレーム / 全フレーム |
|---|---|---|---|
| BS11（ファイル D、1920x1080） | `x=1744,y=22,w=138,h=56`（measurements.md「ロゴの残存」の概算値） | 既定 12 | 6,388 / 54,012（11.8%） |
| MX2（ファイル C、720x480） | `x=600,y=0,w=120,h=40`（「ロゴの残存」で「特定できず」としていた範囲の一角。概算） | 12 | 148 / 98,972（0.15%） |
| MX2（同上） | 同上 | 40（緩めた） | 900 / 98,972（0.91%） |

MX2 はロゴが非常に薄く矩形の確度も低いため、`make-logo` の有効フレーム数自体が少ない（`MIN_USABLE_FRAMES=4` は超えているため失敗はしないが、学習に使える単色背景フレームが乏しい）。

### `analyze --logo` の検出結果

| ファイル | 検出フレーム割合 | 閾値 | `-inlogo` を渡したか |
|---|---|---|---|
| BS11 | 0.792（42,756/54,012） | 0.100 | **渡した** |
| MX2（`--threshold 40` の `.lgd`） | 0.000（0/98,972） | 0.100 | 渡さなかった（フォールバック） |

MX2 は検出フレーム割合が 0 になり、`inlogo_decision` のフォールバックにより `-inlogo` を渡さない経路に落ちた。この場合の `trim.avs`/`detail.jls` は `--logo` 省略時と完全に一致した（バイト単位で diff なし）。**SD 解像度・非常に薄いロゴでは、今回作った `.lgd` の精度では自前検出が機能しなかった**という実例。

### BS11 での `detail.jls` の変化

```
--logo なし:  4428  19832  514   0  514 :L
--logo あり:  4428  19832  514   0  500 :Mix

--logo なし: 21631  44556  765  -1  765 :L
--logo あり: 21631  44556  765  -1  756 :Mix

--logo なし: 48305  48454    5   0    0 :Nologo(cut)
--logo あり: 48305  48454    5   0    5 :Endcard(add)
```

長い本編ブロックが `:L`（情報なし）から `:Mix`（ロゴ有・ロゴ無混合、内部にわずかにロゴ無し区間がある）に変わり、末尾の 5 秒区間が CM 扱い（除去）からエンドカード扱い（保持）に変わった。Trim も 3 区間 → 4 区間になり、余分に残る量は 13.5s → 16.5s に増えた（詳細・設定スイープの結果は [jls-settings.md](jls-settings.md)「ロゴありでの比較・既定値」）。4 列目（15 秒格子誤差）はこのファイルでは元から 0〜-1 フレームと小さく、ロゴ情報による改善は観測できなかった。

### 見ていないこと

- **実ファイルは 2 局・2 本のみ。** 複数局での傾向の一般化はできない（特に MX2 は検出自体が失敗したため、ロゴありでの挙動を実質的に確認できたのは BS11 の 1 本だけ）
- `~/Downloads` 以下の実録画ファイル（BS11・MX2 以外にも局・番組が複数キャッシュに残っていた）は今回の実行環境のファイルアクセス制限により読めず、比較に使えなかった。**入力ごとのキャッシュに `input_prepared.mp4` が既に残っていた 2 本のみ**を使った（この制約が無ければ TOKYO MX や BS日テレでも同様の比較ができたはず）
- MX2 のロゴ矩形は目視の概算（「ロゴの残存」の「見ていないこと」参照）で、位置が実際のロゴとずれている可能性がある。矩形をもっと正確に取れれば検出できたかは未検証
- `autocm_sub`/`param_cuttr` のスイープは BS11 の 1 本のみ（[jls-settings.md](jls-settings.md)参照）。`(cut-cancel)` や冒頭 15 秒×2 の構成が実際に現れる番組では検証していない
- `-CutMrgIn`/`-CutMrgOut` の実測も BS11 の 1 本・`0`〜`20` フレームの範囲のみ（[jls-settings.md](jls-settings.md)参照）
- ffmpeg のフレーム供給と `.dtvi` の `frame_count` の一致検査（自己検証、[architecture.md](architecture.md)）は両ファイルでエラーなく通過したことのみ確認した。不一致時に実際に停止することは別途ユニットテストで検証済み（実ファイルでの不一致は再現していない）

## CM 検出の品質

15 秒格子からの誤差（`detail.jls` の 4 列目）で評価する。

| ファイル | 検出された CM ブロック | 誤差 |
|---|---|---|
| A | 15 + 30 + 15 秒 | 0 / 0 / -1 フレーム |
| B | 15+15 / 15+15+30 / 15+15+30+15 / 15×6 秒 | 0 〜 -4 フレーム |
| C | 120 秒 × 3 ブロック（内部は 15/30 秒の組み合わせ） | 0 〜 -1 フレーム |

**ロゴ情報を一切与えずにこの精度。** 「ロゴなしだと精度が落ちる」の実体は「CM 区間の検出はほぼ完璧だが、その区間が CM か本編かの判断材料が足りない」であることが分かった。

原因と対処は [jls-settings.md](jls-settings.md)。

## elst 除去と A/V 相対時刻（#60）

**すべて `tests/fixtures/gen.sh` の合成フィクスチャ（`sample_elst.mp4`=Opus、
`sample_elst_aac.mp4`=AAC）での実測。実ファイルでの elst 有無・priming 量は未計測。**

architecture.md「未対応の入力」の elst の行がこれまで「除去後の映像・音声パケットが
CRC32 でビット一致することを確認済み」としていたが、これは**ペイロードのみ**の確認で、
タイムスタンプは見ていなかった。以下はタイムスタンプ側の実測。

### 除去操作（回避策コマンド）自体の可逆性

回避策 `ffmpeg -i IN.mp4 -c copy -use_editlist 0 -movflags +faststart OUT.mp4` を
elst 付きフィクスチャに通した結果、映像・音声とも**パケット数・サイズ・CRC32 が
「最初から `-use_editlist 0` で符号化した場合」と完全に一致した**（`sample_elst.mp4`
→除去後 と `sample.mp4` を比較、`sample_elst_aac.mp4`→除去後 と `sample_aac.mp4` を
比較。音声パケット数は Opus 1000 / AAC 937 で除去前後とも変化なし）。
**除去はパケットを一切増減させず、`elst` メタデータだけを消すことを確認済み。**

### `elst` の実値

`ffmpeg -v trace` の `Processing st: N, edit list 0 - media time: X, duration: Y` から採取
（`media_time` はそのトラック自身の `mdhd` timescale、`segment_duration` も同じ
timescale で記録されていた。`duration_ts`/`time_base` と突き合わせて確認済み）。

| トラック | `media_time` | 秒換算 | `segment_duration` | 秒換算 |
|---|---|---|---|---|
| 映像（Opus 版・AAC 版とも同じ） | 2002（timescale 30000） | 0.066733 s | 599580 | 19.986 s |
| 音声 Opus | 312（timescale 48000） | 0.006500 s | 959040 | 19.980 s |
| 音声 AAC | 1024（timescale 48000） | 0.021333 s | 958464 | 19.968 s |

映像の `media_time`（0.066733 s）は、elst なしフィクスチャで実測している**先頭映像フレームの
生 pts オフセット（罠4の `cts_offset` 実測67ms）と一致**した。すなわちこの elst は
「B フレームの並べ替えで生じる先頭フレームの pts 遅延」を打ち消すためのものであり、
サンプルを間引いているわけではない。

### 「先頭の映像 pts − 先頭の音声 pts」の strip 前後比較

`ffprobe -show_packets` の値（elst が付いたファイルは ffprobe 自身が edit list を
解釈した値を返す。素の box 値ではない点に注意）。

| | 映像 pts（先頭） | 音声 pts（先頭） | 差（映像−音声） |
|---|---|---|---|
| elst あり・strip 前（Opus） | 0.000000 s | −0.006500 s | +0.006500 s |
| elst あり・strip 前（AAC） | 0.000000 s | −0.021333 s | +0.021333 s |
| elst 除去後（Opus / AAC 共通、映像側は音声コーデックに依存しない） | 0.066733 s | 0.000000 s | +0.066733 s |

strip によって差は **Opus で +0.060233 s（60.2 ms）、AAC で +0.045400 s（45.4 ms）増える。**
音声側の先頭パケットの pts が「−media_time」から「0」に変わる分（priming をそのまま
含めて音声開始点として扱うようになる）と、映像側が「0」から「+0.066733 s」（生の pts
オフセットがそのまま残る）に変わる分の合算。**ずれは実際に生じる。**

### Opus と AAC で結果が異なる理由（`dOps` の有無）

`ffmpeg -v trace` に出るデコーダのログを比較すると:

- **Opus**: `sample.mp4`（elst なし）でも `sample_elst.mp4`（elst あり）でも
  `skip 312/960 samples` が同一に出力される。Opus の pre-skip はコンテナの `elst`
  ではなく `stsd` 内の `dOps` ボックス（`pre_skip=312`、実測）にコーデックレベルで
  埋め込まれており、**elst の有無と無関係にどのプレーヤーでも適用される**。
  `src/mp4io/write.rs`（1〜7行目のモジュール doc）に明記されているとおり
  `stsd` には一切触れず `moov.clone()` でそのまま引き継ぐため、cut 後の出力でも
  `dOps` は失われない。**Opus は elst を除去しても実際の priming 補正には影響しない。**
- **AAC**: elst なし（`sample_aac.mp4`）では `skip` に関するログが一切出ない。
  elst あり（`sample_elst_aac.mp4`）でのみ `demuxer injecting skip 1024 / discard 0`
  が出る。**AAC は priming を伝える手段が elst しかなく（`iTunSMPB` のような代替タグは
  ffmpeg 純正 `aac` エンコーダでは書かれない）、elst を除去すると priming の情報は
  完全に失われる。**

**何を見ていないか**:
- 実ファイル（放送録画）で elst 付き・priming 量がどうなっているかは未計測（このフィクスチャは
  ffmpeg 合成）。
- AAC の priming が 1024 サンプル以外（issue に書かれている 2048 サンプル等、エンコーダ設定
  依存）になるケースは未計測。ここでの実測値は ffmpeg 純正 `aac` エンコーダ・128kbps 固定。
- 実際に `cut` を通した出力で `dOps`/priming がどう伝播するかは、`cut` 自体を動かした
  E2E ではなく `src/mp4io/write.rs` の doc comment（`stsd` 非改変）からの確認にとどまる。
- 継ぎ目（CM カット境界）ごとの影響ではなく、**ファイル先頭 1 か所だけ**の影響であることは
  elst の `media_time` の定義上ほぼ自明だが、複数区間 cut の実機テストでは確認していない。

### 方針: ずれを許容して記録する

- **Opus**: 対応不要。`dOps` がコーデックレベルで pre-skip を伝えるため、elst 除去は
  実際の A/V 同期に影響しない。
- **AAC**: elst 除去により、**保持した最初の区間がソースの先頭フレームから始まる場合に限り**、
  出力音声の先頭 media_time 分（実測 21.333 ms、他エンコーダでは issue の見積もりで最大 43 ms
  程度）がエンコーダの priming（無効なランプアップ）のまま音声として残る。CM カットで通常
  最初のカット境界以降に生じる継ぎ目の音声選択（罠4の DTS 起点の引き当て）とは無関係の、
  **ファイルにつき高々 1 回・1 フレーム未満・非累積**のずれである。
- `prepare`/`auto` は elst を自動除去してよい。**理由**: (1) 除去操作自体はパケットを一切改変しない（上記で確認済み）、
  (2) Opus は実害がない、(3) AAC の残存ずれは 1 フレーム未満・非累積で、音声を再エンコードしない
  という設計方針（分解しないもの一覧）と両立しない sample 単位トリムをしない限り解消できない
  （AAC はこの実測ではたまたま priming=1 フレームぶんで先頭パケット全体を捨てれば解消できるが、
  Opus の 312/960 のようにフレーム境界に一致しない場合は同じ手法が使えず、コーデック別の
  特別扱いを `prepare` に持ち込む価値がないと判断した）。
- `media_time` を読んで区間選択の起点を補正する対応は**見送る**。上記の理由に加え、対応しても
  「ファイル先頭から始まる保持区間がある場合の AAC のみ」という狭い適用範囲にしかならない。

## 測定コマンド

キーフレーム間隔の統計（デコードしないので速い）:

```bash
ffprobe -v error -select_streams v:0 -show_entries packet=pts_time,flags \
        -of csv=p=0 IN.mp4 \
| awk -F, '$2 ~ /K/ {if(p!=""){d=$1-p; s+=d; n++;
             if(d>mx)mx=d; if(mn==""||d<mn)mn=d} p=$1}
           END {printf "平均%.2fs 最小%.2fs 最大%.2fs 区間数%d\n", s/n, mn, mx, n}'
```

キーフレームのフレーム番号一覧:

```bash
ffprobe -v error -select_streams v:0 -show_entries packet=pts,flags \
        -of csv=p=0 IN.mp4 | awk -F, '$2 ~ /K/ {print int($1/1001)}' | sort -n
```
